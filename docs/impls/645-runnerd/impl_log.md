# runnerd — impl log

Dated log for [#645](https://github.com/yicheng47/runner/issues/645), oldest entry first. [README](README.md) has the condensed state, and [plan.md](plan.md) the phases and missions.

- 2026-10-04 — Spec drafted at Jason's request, as 0.13's sole release blocker, starting from the archived 466 spec and the issue body. It takes the lesson Jason agreed to that afternoon after comparing Paseo and Orca: the state owner must run without the UI, so the daemon runs all of `AppCore` and the app becomes a client. Reading the code showed why the terminal has to move too: the app's `TerminalSession` computes the draft state the delivery gate reads (`observe_parsed` → `report_input_state`), and it answers terminal queries.
- 2026-10-05 — Jason named the process `runnerd`, which leaves "host" to mean a machine. Asked whether the terminal would feel the same: a local Unix socket round trip measured 7 µs p50 and 27 µs p99 at 1.2 GB/s through Python on his Mac. The spec now keeps today's resize behaviour (the mirror resizes at once) and gates 1b and 1c on a benchmark against `main`.
- 2026-10-05 — Asked whether the tmux-era parsing bugs come back. The history: the tmux runtime rebuilt screens from `capture-pane` text, which dropped modes (#150, impl 0009). PR #157 tried a daemon with a headless alacritty `Term` and xterm.js in front, and was closed for four problems ([0011](../archive/0011-pty-host-terminal-runtime.md) §"Why no headless emulator"). Spec 42 recorded the raw-replay workarounds that followed. Two of #157's problems are gone by construction: both sides now run the same crate, and keys are encoded against the mirror. The other two, mode restoration and sequence races, are the exact snapshot boundary and the single per-session lock, with a split-point test #157 never had.
- 2026-10-05 — Found the 2026-08-18 record of this direction in the GPUI rewrite plan, whose motivator was updates killing agents. Proposed four phases, putting updates (a session daemon with a stable protocol) before remote machines, which reuse that protocol over ssh.
- 2026-10-05 — Evaluated #709 at Jason's request: it does not go first. At the pinned 0.26.0, alacritty's `EventLoop::pty_read` parses bytes directly and exposes them only through the `ref_test` file tap, while `runnerd` must forward raw bytes to the app's mirror and to its own observers. #647's deadline fix shipped in PR #710. #709's audit checklist moves into 1b. Plan directory written.
- 2026-10-05 — Jason clarified that alacritty stays: only its I/O layer (`tty` + `EventLoop`) is rejected, which Runner never used. He closed #709 (not planned, with a comment). Checked Windows against the code. The design holds, with four Windows points now in the spec and in 1c: `portable-pty` loads `conpty.dll` from beside the running executable, so it and `OpenConsole.exe` get copied next to `runnerd.exe`; `runnerd` starts with `CREATE_NO_WINDOW` rather than `DETACHED_PROCESS`, so console children never open a window; the pipe gets an owner-only security descriptor; and a CLI inside another Runner session's job, where Runner's jobs forbid breakaway, refuses to start a daemon. Phase 4's open question is whether Windows OpenSSH kills a session's processes on disconnect. The probe could not run because the PC was off.
- 2026-10-05 — Jason asked whether Paseo answers the two Windows ssh questions. It avoids them. Its ssh transport is `ssh -T -o BatchMode=yes -W 127.0.0.1:<daemonPort> <host>` (`packages/protocol/src/ssh-transport.ts`), a pipe to an already-running daemon. Its docs (`public-docs/connectivity.md`) say "It does not install, start, or configure Paseo on the remote host", with starting the remote daemon as a prerequisite. Its own daemon spawns with Node's `detached: true` plus `windowsHide`. Its Claude usage reader takes the macOS keychain only on darwin and reads `.credentials.json` elsewhere. Adopted: `runnerd --stdio` only connects, the remote daemon runs in the user's own logon, and the local CLI never starts a daemon from an ssh session. This also covers Macs, where a daemon started over ssh could leave Claude Code facing a locked login keychain. The phase 4 probes become confirmations.
- 2026-10-05 — Jason: phase 1 does not merge into `main` mission by mission. It goes on an umbrella branch with its own nightly channel. Read how the channels work today: `script/bundle-mac --channel` writes `SUFeedURL`, Windows takes its feed from `RUNNER_RELEASE_CHANNEL` through `release_urls`, `nightly.yml` hard-codes the `nightly` tag and concurrency group, and `ci.yaml` runs only for `main`. Plan: `feat/645-runnerd` with mission PRs against it, rebased onto `main` between missions, no schema change; a `nightly-runnerd` prerelease with the same app identity and install-to-switch (switching back requires stopping `runnerd` first, and 1c makes `runnerd` exit if an older app takes over its sockets); channel infrastructure on `main` first; landing after a week of daily-driving. Proposed keeping 1a on `main`, because it changes no behaviour and is the change most likely to conflict.
- 2026-10-05 — Jason asked whether the backend crate should become `runner-daemon`. Yes, staged. 1a adds `runner-protocol`, which holds the row types from `model.rs` (plain serde and schemars, no rusqlite), the request table and `DaemonClient`. 1c moves `runner-backend` to the app's dev-dependencies, so the compiler enforces that the app holds no backend state. 1d does the rename, when few paths still name the crate. Today the app reaches `runner_backend::ops` 325 times and `::model` 94 times, which is why the rename waits.
- 2026-10-05 — Jason: no downgrade, and very thorough tests before the switch. Replaced "switching back needs one step" with three things. First, a switch gate before his own install moves to `nightly-runnerd`: A, automated tests; B, a development rehearsal with a 24-hour soak; C, a rehearsal on a copy of his database with its `-wal`; D, packaged builds on the PC and in a separate macOS test account; E, the guard. Second, fixing forward after the switch. Third, a downgrade guard on `main`: builds without `runnerd` refuse to start while `runnerd.lock` is held, which needs no protocol. Until the gate passes, channel cuts go only to the PC and the test account.
- 2026-10-05 — Jason: no separate macOS test account. His production install can take the packaged checks. D's Mac half now runs on his install right after the switch; before the switch, cuts go only to the PC.
- 2026-10-05 — Jason: install `nightly-runnerd` on his Mac from the first cut, and fix forward. The switch gate became "the checks before landing", which gate the landing on `main` instead of the install. Kept two protections: a backup of his data directory before the first install, and the downgrade guard on `main` as an emergency exit.
- 2026-10-05 — Jason asked whether `runner-protocol` was needed. It is not, as a crate. The protocol becomes a module of `runner-core`, which the app, the CLI and the daemon already share. The compile-time boundary in 1c is unchanged.
