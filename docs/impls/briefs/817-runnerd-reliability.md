## The bugs

1. **#817 (P1): 10-second deadlines fail app and CLI start while `runnerd` is still starting or stopping.** The app and the CLI give a spawned `runnerd` 10 s to accept connections (`runner-core/src/daemon_process.rs` about :187, `runner-cli/src/client.rs` about :122), other starters wait 10 s for the startup lock (`daemon_process.rs` about :207), and stopping an old daemon waits 10 s for its lock (`daemon_process.rs` about :170, `protocol/managed.rs` about :220–230), while teardown alone may take `SHUTDOWN_TIMEOUT` (8 s, `runner-daemon/src/daemon/server.rs:19`) plus the resume and runtime steps after it. A Windows CI run on a docs-only commit failed four `crates/runner-cli/tests/daemon_process.rs` tests this way. Expected, per the issue comment: a daemon that exits fails fast (poll `child.try_wait()` in the connect loop and report its exit status with the `runnerd.log` path); a live but slow daemon gets a longer start deadline (for example 30–60 s); the startup lock's wait derives from the same deadline; the stop waits derive from `SHUTDOWN_TIMEOUT` plus the steps after it. Name the deadlines as constants in one place rather than repeating literals.
2. **#815: an accept error stops `runnerd` and every live session.** The accept arm of the serve loop (`server.rs` about :201–210) cancels the daemon on any `Err`, which runs the full teardown. Triggers: a Windows client that opens and closes the pipe before `ConnectNamedPipe` (`runner-daemon/src/ipc.rs` about :56–68), and `EMFILE` on macOS, where an app-started daemon inherits launchd's soft limit of 256 descriptors. Expected: log the failed accept and keep serving, with a short pause so a persistent error does not spin; only an explicit stop, the OS shutdown signal or the endpoint-ownership check ends the daemon. Follow the sentinel's existing pattern in the same file (`discard_sentinel_connection` and its test `sentinel_accept_errors_back_off_and_return_to_serving`). Also raise the soft `RLIMIT_NOFILE` toward the hard limit at `runnerd` start on Unix, logging the result, as the issue suggests.
3. **#816: a fork that outlasts the 10-second request deadline reports failure, then completes.** Every request gets `REQUEST_TIMEOUT` (`runner-core/src/protocol/socket.rs` about :12, :530–544), but `session_fork` waits up to `FORK_MATERIALIZE_TIMEOUT` (120 s, `runner-daemon/src/session/manager/spawn.rs:7`). Expected: a request's client deadline covers the daemon's own upper bound for that request. Prefer the issue's first option: use the existing `fast` flags in `protocol/api.rs` (currently unread by the transports) so non-fast requests get a longer deadline, and give `session_fork` more than its 120 s materialization bound. Keep the app's fork error path (`runner-app/src/surfaces/chat.rs` about :183, :225–236) for real failures.
4. **#819: the crash notice says "1 sessions stopped".** `crash_recovery_message` (`runner-app/src/lifecycle.rs:170`) does not pluralize; match the other lifecycle captions ("1 session stopped").
